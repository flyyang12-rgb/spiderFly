## 2. 维护时怎么做

1. 先读 README、CONTEXT 和相关台账条目，查看当前代码与未提交改动。既有说明可能过时，用实际行为核查，并记录差异。
2. 新问题先写清“什么场景、发生了什么、影响谁”；关联已有编号，确实不同的问题再新增编号。
3. 开始实现时，更新该条目的范围和状态。只做其中一部分，就拆出子项或把未完成部分写明，不提前标记整项完成。
4. 验证后记录实际修改文件、验证方式、结果和未覆盖场景。只读代码检查、自动测试、真实页面验证、业务验收分别说明。
5. 完成当前改动时同步更新受影响的文档。README 与使用说明只增加已经可用的行为；候选设计继续留在设计文档和台账里。
6. 在下方维护日志补一条短记录，写清变化及对应编号。没有新的变化时，不为更新时间而反复改写文档。

已有授权和用户偏好继续有效；写入台账不等于授权执行台账中的全部业务操作，也不意味着后续每个可逆维护动作都要再次询问。

### 复测与交接

先记录当前工作区改动和所用 wheel 的版本、摘要。只有提交号不足以重现含未提交改动的检查；本次代码范围与证据索引见[项目检查记录](项目检查记录_2026-09-03.md)。

后端测试会导入 app，配置模块会读取项目根目录的 .env；需要覆盖平台的检查，按本轮方式先准备隔离副本：

1. 保持项目相对目录结构，复制 backend、flows、examples、sample_scripts、docs、README、CONTEXT、使用说明、.env.example 和 release/instructions 中需要的 wheel。排除真实 .env、data、共享工作区、现有虚拟环境与缓存。
2. 在测试目录创建独立 Python 3.12 环境，安装副本 backend/requirements.txt 和待测 wheel；本轮实际安装版本为 0.1.4，不使用开发目录链接代替安装包。
3. 从运行测试的子进程环境中移除继承的 SPIDERFLY_*、FEISHU_*、PYTHONPATH、PYTHONHOME；核对配置指向副本，并使用副本内的数据、环境和工作目录。这些设置只用于测试进程。
4. 使用上述测试环境的解释器，在副本 backend 目录运行全套检查；只验证相关修复时可运行定向检查。以下 python 均指该测试环境，不是在正式运行目录执行。

```powershell
python -X utf8 -m unittest discover -s tests -v
python -X utf8 -m unittest tests.test_project_audit -v
```

5. 页面验收另用只监听本机的临时服务、测试账号和合成任务，关闭通知；服务单实例锁使用独立测试 key。前端构建到临时目录。验收结束后关闭临时服务，保存实际测试日志、结果和下载摘要。

不把全套测试当成每次文档编辑的必经步骤。纯文档修改核对内容、引用、代码位置和链接即可；代码修复先复现对应问题，再按受影响范围验证。跳过项写明具体测试与原因，环境准备完成后再补测。

交接时分别写清：代码是否已修改、检查是否已通过、正式服务是否已加载，以及还有哪些场景尚未验证。原始证据保留当时结果，后续补充另留说明，不把文档核对说成重新跑过代码。测试材料在仓库外保留，公开维护文档只放必要结论与不含敏感信息的索引。

## 3. 状态怎么理解

| 状态 | 含义 |
| --- | --- |
| 候选 | 已记录问题和建议，尚未开始该项实现 |
| 进行中 | 正在实现约定范围 |
| 待验证 | 已有修改，但该项要求的验证尚未完成 |
| 已完成 | 约定范围已完成，且有与验收对应的验证记录 |
| 暂缓 | 暂时不投入，写明原因和重新考虑的条件 |
| 已取消 | 已决定不做，保留原因和历史 |

“文档已写”“已有接口字段”“代码能启动”都不能单独作为功能完成依据。没有真实场景只能验证的事项，应说明验证边界；不把未运行的测试写成通过。

## 4. 新优化条目的模板

编号持续递增，删除或取消后不把旧编号分配给别的问题。先在台账总表登记状态，再增加以下详情。

```text
OPT-编号 优化名称
问题：谁在什么场景遇到什么不便或错误？
现状依据：文件链接、相关函数、已观察到的行为；推测需明确标注。
最小建议：最小可以解决该问题的改动，以及暂不涉及的部分。
验收：使用者可以观察或有针对性地验证的结果。
前置条件：关联条目，或需要明确的业务规则。
实现与验证记录：日期、实际改动文件/提交、验证方式和结果、剩余限制。
```

优先级是排序建议，不代表交付日期。新增点位不要求个人签名；维护联系方式可以按协作需要补充，不作为指令运行条件。

## 6. 文档核查要点

- 相邻项目、参考仓库和 SpiderFly 的实现状态分别描述。
- 文件链接尽量使用仓库内相对路径，并写相关函数名，减少行号变化造成的误导。
- 引用外部实现时保留核查日期或固定提交；旧 README 的陈述不优先于当前代码。
- 真实账号、密码、会话、业务文件和运行截图不复制进公开维护文档；需要证据时使用脱敏描述或受控资料引用。
- 修改 Markdown 后检查内部链接、条目编号和术语一致性；纯文档更新无需因此运行真实业务。
- 新会话可以从 CONTEXT 进入；实际实现前仍需按当时的代码和用户指示核查，而不是机械执行旧台账。
