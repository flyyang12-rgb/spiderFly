# 任务需求与版本方案

状态：2026-09-09 已实现版本入口和验证流程，正式服务尚未加载本轮代码。当前能力以 [AI 任务助手](AI任务助手.md) 和 [CONTEXT](../CONTEXT.md) 为准。

## 职责

| 部分 | 职责 |
| --- | --- |
| 用户 | 决定业务目标及变更，必要时确认具体歧义 |
| AI | 读取任务要求和知识，生成代码、试跑、分析和修复错误 |
| 知识库 | 保存工具用法、示例和限制；不作为任务进度存储 |
| Python 脚本 | 实现提取、筛选、去重、排序和导出，固定业务参数 |
| 采集接口 | 调用 Scrapling/Playwright，统一网络、会话、并发限速和断点 |
| 平台 | 持久保存需求、版本、计划和执行快照；负责队列、验收、维护预算与通知 |

正常定时运行直接执行已保存的 Python，不重新询问模型。单任务 HTTP 采集并发与平台任务串行队列是不同层级。暂不增加 DP、Node.js 入口或平台 Excel/浏览器资源接管。

## 任务要求

每个任务独立保存可查看的当前要求及变更历史，包括输入、站点、范围、数量、字段、筛选、排序、并发、输出和验收；不适用的字段可留空。AI 每次生成或修复都读取该记录，不依赖用户记忆或最近聊天。

用户上传代码但没有说明时，目前静态提取模块说明、明确常量及验收声明中的用途、输入和输出，标注“从代码推断”；无法判断的标记“未说明”，不编造、不阻止正常运行。来源应区分用户明确要求、代码推断和未说明。推断不能自动升级成用户确认的验收条件。

只针对影响结果的歧义提问，例如“原要求是杭州，新代码改为上海，是否同步修改城市？”用户明确提出的修改直接处理，不重复要求确认。用户只改一个字段时，其余要求保持原值。

## 需求修改与错误修复

| 类型 | 处理规则 |
| --- | --- |
| 用户明确修改需求 | 保存新的需求版本，据此生成、验证并启用代码 |
| 自动修复报错 | 保留原需求与验收，只修正错误，不减少数量、删除字段或放宽条件 |
| 人工上传与原需求一致 | 保存新版本并验证，通过后启用 |
| 人工上传与原需求冲突 | 保留上传版本，只询问具体业务差异，未解决前不启用 |
| 没有明确需求 | 保留原业务逻辑、修正错误；运行通过不等于业务意图已确认 |

## 更新与版本编号

AI 对话修改不需要用户下载再上传，由平台保存新版本并验证。人工在本地修改时，可下载任意历史版本的单文件 `.py`，通过原任务“更新脚本”上传，依赖单独声明。入口位于 AI 助手的“维护与版本 → 代码版本”。

版本不可变，保存来源、基于哪个版本、需求与参数快照、源码、依赖及对应环境。编号只递增，不因回退而重用：最高 V2 时新修改为 V3；已有 V3、当前回退到 V2 时新修改为 V4。重复提交完全一致的内容及配置沿用去重机制，不能覆盖历史版本。

上传原文件保留。若 V4 验证发现代码错误，AI 修复后另存 V5，V5 验证通过后启用；不能覆盖 V4。新版本失败时不切换，保留当前启用版本。保留版本不代表它一定能正常运行，当前版本本身有错仍应记录失败。

依赖没变时复用匹配环境；依赖改变时先匹配已准备的受限环境并试跑；自动准备任意依赖环境仍不支持。只有准备和验证全部通过后，代码、需求、参数和环境才一起切换。环境不支持时明确失败原因，不用不兼容环境强行执行。

## 启用、排队与回退

正在运行的执行继续使用原需求、参数、源码和环境；已结束的记录保持历史事实。新版本验证通过后，后续执行及同任务尚未开始的排队记录切换完整版本快照，保留发起人、触发信息，不重复入队、不改变原定时计划。

版本启用与待执行记录衔接应在一致的事务边界完成，防止源码和需求错配。旧修复不能覆盖用户的新上传或新需求；明确记录候选所基于的版本。

回退恢复代码、需求、参数及环境，保留定时计划。正在运行的执行不改变，待运行记录同步回退。回退到某版本不意味着复用它以前的采集断点，仍按当前断点兼容条件处理。

## 失败、群通知与人工处理

程序失败后默认 AI 维护，验证通过才启用修复，并按原机制自动重跑一次。修复失败或重跑仍失败，保持实际失败状态、完整错误和产物，通过已配置的群通知告知团队，由团队人工处理。

需要区分原执行失败通知与最终维护失败通知；最终维护结果已单独接入已有群配置；测试使用模拟通知，不向真实群发测试消息。发送失败应记录，不能显示“已送达”；不得新增无限发送循环。

保留原定时计划，下次到点仍执行当前启用版本。用户主动停用后不再调度，不新增“修不好自动停用”或额外升级处理机制。同类故障去重和原维护预算继续生效，不因定时再次失败而无限调用模型。

## 清爽展示

默认只显示状态、实际结果、一句修改说明和必要操作。任务要求、历史版本、代码差异、原始日志、用量按需展开。以下为目标文案例子，不是已执行记录：

- “采集数量从 100 条改为 200 条，新版本已启用。”
- “修正翻页定位，自动重跑成功，采集 100 条。”
- “新版本缺少薪资字段，验证未通过，继续使用原版本。”
- “修复未通过，本次运行失败。原因：……”
- “已切换至 V3，等待执行。”

不以试跑通过冒充正式重跑成功，不以保留旧版本冒充任务恢复正常。

## 开发顺序与验收

| 顺序 | 实现内容 | 必须验证 |
| --- | --- | --- |
| 1 | 需求持久保存、来源及历史 | 长对话不丢要求；代码推断不成为强制业务验收 |
| 2 | 完整版本快照、下载与原任务上传更新 | V3 回退 V2 后新上传为 V4；原文件不覆盖；依赖环境匹配 |
| 3 | AI 需求修改与上传失败维护 | 明确修改直接处理；冲突只问差异；修复不放宽要求 |
| 4 | 新版启用、排队衔接和完整回退 | 运行中版本不变；待执行整体切换；计划与历史保留；重启不重复入队 |
| 5 | 最终维护结果群通知与简洁展示 | 修不好保持失败、通知有实际结果、计划保留、模型预算不失控 |

每一步完成后更新实际状态。使用隔离数据验证，正式备份、部署、代码提交及推送分别记录，不能把方案确认写成实现完成。
