# DeepSeek 任务助手与自动维护

管理员在任务中心点击“AI 创建”，描述采集或表格处理需求。已有任务通过行内“AI 助手”打开自己的对话。各任务使用同一后台 AI 服务，但对话、处理记录和 Python 草稿分别保存。关闭页面后已提交的一轮继续处理，重新打开可查看记录。

## 配置与操作

1. 超级管理员打开“管理中心 → AI 模型”，填写 DeepSeek API 密钥并保存；留空保留原值。测试连接只访问官方模型列表，不生成内容。密钥不会回显。
2. 选择模型，在“调用与维护预算”展开每轮时间、模型调用次数、输入和输出 Token 预算，点击“保存配置”。自动维护的滚动总限额使用单独的“保存维护预算”。新提交的一轮保存这些配置的快照，已提交的一轮不受后续预算修改影响。默认使用 `deepseek-v4-pro`，也可选择 `deepseek-v4-flash`；实验视觉模型可选，但当前工具没有截图输入能力。
3. 创建 AI 对话，写明网址、范围、条件、输出字段和校验标准。工具按需检索知识、读取用户明确给出的公开网页、读取本任务及最新草稿、检查 Python 语法并保存草稿。
4. 查看代码或下载 `.py` 与 `requirements.txt`。点击“使用草稿”后，检查脚本、依赖和说明；处理表格时在原表单上传模板。草稿默认带入手动运行设置，通知默认关闭。
5. 点击“创建任务”后沿用原环境准备流程，再手动运行并检查业务结果和文件。新建任务成功时对话自动关联该任务。已有任务的修改草稿通过“创建测试任务”试跑，不替换原任务源码。

草稿卡片显示“语法通过 · 未试运行”。该标签只说明保存草稿时的静态检查；即使之后在任务中心成功运行，草稿也暂不自动关联运行验收记录。业务是否成功要查看对应执行记录、实际文件和原业务校验。默认只显示最新草稿，历史草稿、长回复、处理记录、用量和维护版本按需展开；模型默认用三句话以内说明结果。

## 本版边界

- Python 仍是正式任务入口，正常成功的定时执行不调用 DeepSeek。一个 AI 后台处理开发请求及维护分析；维护试跑与业务运行共用同一个串行执行队列。当前运行结束后先验证已就绪的修复，再启动下一条排队记录。
- 页面读取仅支持公开 HTTP/HTTPS 文本，不携带登录会话，不执行 JavaScript。用户提供的域名逐次校验，拒绝本机、内网地址及未授权重定向。登录页、验证码、拒绝访问都不能视为业务数据。
- 对话开发工具不直接执行或发布脚本，也不操作桌面、登录浏览器、设置定时或发送消息。独立的自动维护流程可受限试跑并条件启用修复版本，见下节。普通成员不能使用 AI 入口或模型配置；管理员只能访问自己的对话，超级管理员可访问已知对话。
- `max_seconds` 是一轮的墙钟预算；`max_calls` 限制模型请求次数；`max_tokens` 控制整轮模型输入与输出。请求前保守估计输入长度，可能提前结束以避免超额；页面显示服务实际返回的 Token 用量。工具文本占用后续模型输入预算。没有金额账单；自动维护另有滚动 24 小时总限额，不包含日常对话开发用量。
- “停止”阻止后续工具及模型调用，保留已有草稿。已发出的 HTTP 请求可能还在服务商处理，停止不能撤回这部分计费。服务重启将运行中的 AI 轮次标记中断，不自动重复发送；尚未开始的排队轮次保留。
- 对话全文持久保存，但模型自动上下文为最初需求与最近 20 条消息。最新草稿可通过工具重新读取；超长项目的自动摘要、完整需求检索和结构化参数表尚未实现。

## 文件和版本

数据库新增 `ai_threads`、`ai_turns`、`ai_messages`、`ai_events`、`ai_drafts`。草稿版本递增，源码和依赖完全相同则复用原草稿，不构建环境；因此修改 10–20 次草稿不会产生 10–20 套 Python 环境。通过原创建表单建立多个测试任务时，每个任务仍按现有机制创建独立环境。

对话草稿和任务代码版本分别管理。任务入队时保存源码与依赖的去重版本，执行快照引用版本编号；相同模板也按内容摘要保存一份。维护只新增不可变的候选文件，不覆盖上传原文件，不重复构建 10–20 套环境。管理员可在任务 AI 助手查看各版代码，回退到原始或已验证版本；任务排队、运行或版本文件已改变时拒绝直接回退。上传同名 `.py` 仍是新建任务，不表示升级原任务。

服务配置位于 `data/ai/settings.json`；Windows 密钥位于 `data/secrets/deepseek.key.dpapi`，由运行服务的 Windows 用户通过 DPAPI 加密。切换服务用户或换电脑后需要重新配置密钥。其他环境可配置 `DEEPSEEK_API_KEY`，优先于文件；该变量不会传入业务任务和安装依赖的子进程。API 仅使用固定官方地址 `https://api.deepseek.com`，不接受模型指定的网关地址。

备份需包含实际配置的数据目录；对话与源码也属于本机资料。不要将数据库、密钥、配置、任务源码或结果提交 Git。原上传任务仍按既有 Windows 权限运行，独立 venv 不是操作系统沙箱；修复候选和已启用修复采用下述隔离环境。

知识在 `backend/ai_knowledge/`，首版包含平台入口约定、公开页面采集与表格处理说明，来源和核对日期写在文件内。这里是随代码维护的工具知识；运行后的经验自动归纳与审核入库还没有启用。

## 失败后自动维护

用户不需要开启维护。新提交的任务执行失败后，系统保存原版本、任务说明、依赖、验收条件与模板引用，读取真实错误，自动分析并保存一个修复候选。原来的成功和失败执行记录不被改写。重复的相同故障 24 小时内只维护一次，停止执行和网页访问受限等情况不会无限进入代码修复。

维护完成、失败、预算耗尽或服务中断，都会在“维护结果”留下结论。任务归属人和超级管理员分别收到站内未读提醒；阅读别人的副本不会清除归属人的提醒。离线时仍保存通知，下次登录查看。执行日志直接显示修复结论，管理员还可在任务“AI 助手 → 维护与版本”展开查看过程、实际用量和代码，必要时点击“停止本次维护”或回退。没有单任务维护开关；现有任务启停仍管理原来的定时任务。

普通脚本没有验收声明也可以自动修复：先检查候选保留原函数、调用和校验，在隔离环境用冻结输入复现同类错误，再确认修复后运行通过。不能靠删除逻辑、增加异常吞掉错误或空脚本获得发布。此分支记录“原错误已复现，修复后运行通过”，不把进程成功写成未声明的业务规则已验收。有原业务验收声明时，继续执行冻结的文件、字段、行数等检查，并要求原声明仅生成产物。

修复通过后自动启用并重跑一次，不要求再次确认。正在运行的任务先结束；同任务尚未开始且源码、依赖及输入相同的排队记录自动改用修复版本，并沿用最早一条作为重跑，原参数和发起人保留。没有兼容排队记录时，新建“修复重跑”执行，不额外扣减原计划次数。发布、入队、维护关联同一事务提交；重启继续已有队列，不重复入队，不补跑升级前的历史修复。仅改名称、说明或计划不会阻止修复。若用户已换了源代码、依赖、模板或主动回退，本次旧版本维护结束，新版本失败时继续自动维护。

执行日志、维护记录和通知默认用一句“把 A 改为 B，解决 C”说明修改及效果，追加实际重跑状态：等待、运行、成功、失败或取消。只有正式重跑成功才显示“自动重跑成功”；历史记录没有重跑时仅显示“试跑通过”。“查看重跑日志”可直接打开这次执行的输出与文件。“技术详情”展开原始过程和已确认用量，“代码版本”展开版本及回退。维护通知等重跑结束后保存，关闭浏览器不影响；原失败记录及错误输出保持历史事实。用户已停用任务或重跑预算不足时直接说明未重跑的原因。依赖不兼容、不能复现同类错误或候选未通过检查时保留原版本。

原脚本可使用 `SPIDERFLY_ACCEPTANCE` 字典常量，或一行 `# spiderfly-acceptance: {...}` JSON 注释，声明真实业务约定：

```python
SPIDERFLY_ACCEPTANCE = {
    'effects': 'artifacts_only',
    'file': 'result.csv', 'format': 'csv',
    'min_rows': 5, 'max_rows': 5,
    'required': ['title', 'price'],
    'unique_by': ['title'], 'positive': ['price'],
    'equals': {}, 'urls': ['https://books.toscrape.com/']
}
```

上述 5 行及字段只是例子，应按真实需求填写。`effects` 表示业务仅生成产物，不能用于发消息、写数据库、覆盖原文件或 Windows 桌面操作的任务。AI 创建时可根据明确需求生成此声明；验收不完整时应先补全需求。平台在模型之外检查 CSV/JSON/XLSX 的行数、必需字段、唯一性、固定值和正数，并尊重脚本的失败回执。它只证明声明中的条件，不能代替未表达的业务规则。

一次维护只保存一个候选；分析墙钟预算最多 15 分钟，单次试跑最多 120 秒。单任务滚动 24 小时最多 45 分钟，全局默认 2 小时及 200,000 tokens，可由超级管理员在 AI 模型页调整。自动重跑最多一次，运行上限取剩余维护预算与 120 秒中的较小值，耗时计入维护预算。开始时预留额度，结束后按实际耗时释放；服务中断且实际耗时缺失时保守计入预留值。模型调用超时或重启导致用量未知时，保守保留其 Token 预留，不把它冒充已确认用量。排队等待时间不计作运行耗时。重跑失败不再触发新一轮修复和重跑，直接记录实际结果并通知。

## 受限运行环境的准备与范围

Windows 宿主机需有 WSL Ubuntu，服务使用的 Windows 用户能运行该发行版。管理员在明确的项目目录运行一次安装脚本：

```powershell
wsl -d Ubuntu -- python3 /mnt/d/你的项目路径/SpiderFly/backend/sandbox/setup_runtime.py
```

请替换实际的 WSL 项目路径。脚本从 Ubuntu 官方仓库获取 bubblewrap，从 PyPI 安装固定版本库到当前 Linux 用户的 `~/.local/share/spiderfly-sandbox`，不修改全局 Python；再次运行保留已存在的版本。该用户运行环境需随部署单独准备，不包含在 Git 或 Windows `.venv` 内。未准备好时原任务继续沿用原运行环境，维护会报告无法试跑。

`readonly-v1` 使用 Linux Python 3.12、bubblewrap 命名空间和 seccomp：不挂载 Windows 文件或用户目录，不继承凭据，没有直接外网或子进程能力。只给候选明确保存的网页内容、只读上传模板和临时产物目录；试跑退出后销毁临时目录。内存 512MB，产物最多 20 个且合计 8MB；XLSX 验收限制解压内容 32MB 和 200 列。停止请求会阻止发布，但可能需等待受限子进程的截止时间才释放队列，最长约一次运行上限。

支持标准库及 `requests==2.32.5`、`openpyxl==3.1.5`、`beautifulsoup4==4.13.5`。`requests.get` 和 `urllib.request.urlopen` 读取验收声明中完整 URL 对应的冻结响应；不提供任意网络、动态翻页、登录 Cookie 或浏览器控制。原 Windows 任务失败后的网页验收快照在维护开始时获取；已切换到受限环境的任务，则复用失败执行时保存的快照。无法获取快照会报告原因，不能把验证码页当业务数据。

启用修复后，正式执行同样使用此受限环境，重新读取声明的公开页面；有原验收条件时每次独立验收，否则检查退出码及脚本业务回执。没有把 Linux 试跑结果当作 Windows 环境兼容性证明。带浏览器、原公共 wheel、Windows GUI 或其他依赖的脚本可以得到代码候选，但当前不能自动试跑和启用；不为适配环境悄悄删掉必要业务步骤。桌面依赖、通用浏览器、Scrapling 运行时等扩展仍在后续范围。

代码及去重模板保存在 `data/apps/<应用ID>/`，模型记录、执行快照和通知在数据库，维护试跑日志、验收文件与网页快照在 `data/maintenance/`。维护期间不能删除任务；结束后整项删除会清理这些维护资料。备份要包含完整数据目录。

## 已讨论的后续设计

以下是完整演进方向；已实现的子集以上文为准，其余仍待实现：

| 环节 | 约定方向 |
| --- | --- |
| 通用执行环境 | 保留 `.py` 入口，在其下封装 Scrapling、浏览器、Node 等能力；按任务声明工具与依赖 |
| 任务状态 | 持久保存需求、结构化参数、原校验、业务步骤、进度和断点；每次运行绑定实际参数与完整版本 |
| 知识和工具 | 可检索、可直接调用，运行验证过的经验沉淀入库；适用于网页采集及表格处理 |
| 发布版本 | 源码和依赖不可变、相同依赖环境可复用；测试通过后切换，旧执行保留原版本并可回滚 |
| 故障恢复 | 普通重试最多 2 次；Agent 恢复最多 15 分钟、3 轮；仍失败时最多生成 1 个修复候选，额外验证上限 30 分钟 |
| 夜间约束 | 已提供单任务 45 分钟及全局默认 2 小时 / 200,000 tokens 滚动限额；金额账单、按模型定价尚未实现 |
| 自动启用 | 初期只允许只读采集，必须通过原业务校验及兼容检查；表格写入等操作另行按幂等性约束 |
| 页面结果 | 业务步骤、采集/处理数量、错误位置、恢复次数、正式版本与真实模型用量统一显示 |
