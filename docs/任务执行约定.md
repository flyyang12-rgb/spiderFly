# 任务执行与维护约定

这是维护代码时需要遵守的行为约束。平台与业务边界见 [项目架构](项目架构.md)。

人工候选版本确认、AI 对话管理和时长设置另有本机待发布改动；本次架构发布不包含它们。以下涉及人工确认的规则是当前工作区的维护目标，不能据此认定 GitHub 发布版已具备对应界面。已发布能力以同版本源码和使用说明为准。

## 自动维护与版本

- 用户已明确：任务失败后默认维护，验证通过后直接启用修复并自动重跑一次，完成后告知；不提供单任务维护开关，不为同一次已授权修复再次要求确认。普通脚本不能仅因缺少业务验收声明而停留在候选阶段。
- 无验收声明时，按现有流程检查最小修复、用冻结输入复现同类错误、确认修复后运行通过；有原业务验收时继续执行冻结条件。不得删除调用、校验或吞掉异常来假装修好，也不把运行通过写成未声明的业务规则已验收。
- 维护试跑与任务执行共用串行队列。正在运行的任务先结束，再优先验证已就绪修复；同任务同源、依赖及输入一致的待运行记录自动改用新版本，保留发起人、触发信息及参数并记录衔接。不要把普通排队情况作为“有碰撞”交回用户处理。
- 修复发布、重跑入队和记录关联必须在同一事务完成。优先沿用最早的兼容排队记录，否则新建“修复重跑”执行；原失败记录不改成成功，原计划不额外扣次。重跑完成后才发维护结果通知，日志区分等待、运行、成功、失败和取消，并提供重跑日志入口。服务重启不重复入队，升级不补跑历史修复；用户已停用的任务不自动重跑。
- 名称、说明及计划编辑不阻止修复。真正更换源码、依赖、模板或主动回退后，结束旧版本维护，新版本失败时继续维护；旧候选不能覆盖新内容。代码版本按内容去重，修复保存新文件并切换引用，不覆盖原上传文件或为每版重建环境。
- 维护结论默认用一句“把 A 改为 B，解决 C”说明具体修改及效果，仅验证通过后补充运行结果；版本状态单独展示。执行日志、维护记录和通知采用相同简短结论，“技术详情”展开原始过程及已确认用量；原执行的失败状态及 stdout/stderr 保持历史事实。维护结果持久保存，任务归属人和超级管理员各有未读通知。自动维护记录仍在助手的“维护与版本”，人工版本历史、上传、切换和回退统一放在“编辑任务”。
- 相同故障去重、滚动预算及停止约束继续生效。当前默认单任务 24 小时最多 45 分钟，全局 2 小时 / 200,000 tokens；自动重跑受剩余维护预算及 120 秒上限约束，预留与实际耗时均计入预算。一次修复只自动重跑一次，重跑失败不得触发修复重跑循环，保留实际结果并通知。配置由超级管理员在“AI 模型 → 调用与维护预算”维护。
- 修复试跑及启用后的执行使用同一 WSL Ubuntu 环境：普通维护用 `readonly-v1`，声明的公开采集任务用 `collection-v1`，单次运行最多 120 秒；原任务的 Windows 独立环境与此不同。通用登录浏览器、Windows GUI、其他未支持依赖的自动修复仍未实现。具体安装与依赖范围见 [受限运行环境](AI任务助手.md#受限运行环境的准备与范围)。

## AI 采集

- 现有 AI 入口通过 test_collection 对保存的单文件 Python 草稿试跑，必须使用同一串行队列，不能从 AI worker 并发启动业务代码。试跑结果绑定草稿，不能把旧版本通过状态展示在新源码上。
- 生成脚本通过内置 spiderfly_collection 接口采集，保持 Python 入口；不增加 Node.js 入口；2026-09-11 用户授权增加 drissionpage-v1 原生 DP Python 可选方案，规则见 [DP 任务](功能地图/DP任务.md)，不把受控采集解释为 Scrapling 全接口或稳定风控绕过。安装与限制见 [AI 采集环境](AI采集环境.md)。

- 核心环境安装目录为 spiderfly-collection-v2，脚本标记保持 collection-v1 兼容。原生请求通过可信通道固定 DNS/IP、逐跳验权；不允许生成代码直接联网。crawl 提供每页原子断点与 1–4 并发，平台队列仍串行。
- 正式断点按任务及源码/依赖/验收/域名指纹隔离，草稿另存，维护验证只用临时断点。成功且原结果验收通过才清理，下一次计划重新采集；不能把断点恢复写成自动无限续跑。恢复不复用 Cookie。知识、日志中须明确原生引擎与平台适配层的区别。

### 对话要求如何落到脚本

- 用户通过对话指定采集方式、并发数、字段、筛选、排序和恢复要求；Agent 必须落实到保存的 Python 源码及对应接口参数，不以口头答应代替实现。保存后试跑，说明实际配置和结果；超出能力时说明限制，不悄悄改小目标。
- 并发指单个任务内的 HTTP 取页，crawl 支持 1–4，默认 2。用户未指定时根据页面依赖选择，不能把所有采集都默认解释为并发；只有一个待采链接或需要逐页获取下一页时，可能没有可重叠请求。同一命名会话内串行，不承诺浏览器操作或多个任务并行。
- 对话先保存草稿；用户明确修改既有任务时通过 submit_task_update 生成候选版本，验证通过后等待用户确认使用，不直接修改计划或当前版本。创建并保存任务后，定时执行沿用已确认脚本及参数，正常运行不重新询问模型。失败后的自动维护修复仍按既有授权在验证后自动启用并重跑，不进入这次人工确认流程。

## 任务需求与版本

完整规则见 [任务需求与版本方案](任务需求与版本方案.md)。版本入口已实现，正式服务加载状态以 CONTEXT 为准。当前支持准备好的 readonly-v1 / collection-v1 受限依赖，以及 drissionpage-v1 原生 Windows DP 依赖，未知环境明确失败；不承诺任意 Windows 脚本都可受限验证。

- 分开记录用户要求、代码推断和未说明；无需求说明不阻止正常运行，推断不成为用户确认的业务验收。
- 需求变更与报错修复分层；明确修改不重复确认，修复不放宽原条件，上传冲突只问具体差异。
- AI 修改及人工上传使用同一候选版本验证流程；验证通过后由用户确认使用，确认前当前版本不变。支持任意历史 PY 下载、原任务更新脚本；编号始终递增，回退后不复用编号，上传原文件不覆盖。
- 启用与回退联动需求、参数、源码和环境；正在运行的保持原快照，待运行记录同步新快照，计划及历史保留。依赖相同复用环境，依赖变化先匹配受限环境、验证再切换；保留历史版本引用的原生环境。
- 上传新版本报错也默认维护，修复另存版本；修不好不启用，新旧版本的实际错误均保留。最终维护失败接入已配置群通知，由用户团队人工处理，保留原计划，不增加自动停用或升级流程；继续执行去重和预算限制。
- 默认只展示一句具体修改与实际结果，详情折叠。当前状态、待实现功能和历史验证必须区分。


## 浏览器探索（2026-09-10）

用户已授权 AI 主动探索目标网站。沿用现有 Agent 循环，通过 ai_browser 的固定工具操作独立 Windows Chromium；不在 Windows 主进程执行模型生成的 Python/JavaScript。浏览器可用于页面搜索、筛选和数据提取；登录/验证由用户在宿主机完成，再显式继续。浏览器实际发现的公开站点和资源域名可进入同对话的 fetch_page/test_collection；这是对前文仅手工 URL 范围的补充。生成业务脚本仍走原串行队列，探索会话不等于 WSL 定时脚本具备登录态。浏览器结果、观察和等待状态按对话隔离；关闭或重启后不能声称旧会话仍可用。

原生采集补充：AI 优先使用 ai_scraping 的 Fetcher/无头 StealthyFetcher 和快照提取工具，仅在需要交互时打开可见浏览器。旧观察摘要化以控制上下文；实际未达到数量不得声称完成。原生探索成功不代表 WSL 定时脚本已经支持同样引擎或登录态。

仅探索方法时，以自主观察、工具选择、失败调整和证据复核验收，少量样本即可，不强制采满数量或保存脚本。仅解释已有结果时可引用历史证据，不强制重新采集；区分观察与原因假设。生成、修改或定时运行任务时才沿用草稿及试跑要求。当前完整网络响应仅在会话内保留，重启后不能宣称原始证据已恢复。

## 原生 DP 任务（2026-09-11 授权补充）

DP 草稿、版本验证、维护和保存后运行共用串行队列与同一原生执行器，读取普通任务 SPIDERFLY_BROWSER_PORT，默认 9123。占用时不接管；平台只结束本次创建的进程树。原生 Python 子进程具有宿主机账号权限，不是 WSL 沙箱，域名声明不构成网络隔离。仅使用授权任务代码。每次匿名新资料目录，不复用探索登录态。
