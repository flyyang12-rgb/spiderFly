# 多宿主机调度参考实现对照验证

验证日期：2026-09-20。
需求基线：[多宿主机调度需求](多宿主机调度需求.md)。
参考仓库：`flyyang12_rgb_kk-rpa-dashboard` 和 `flyyang12_rgb_kk-rpa-monorepo`。

本报告核对参考仓库，不代表 SpiderFly 当前实施进度。随后完成的首增量见[当前能力](功能地图/宿主机与远程运行.md)和[验证记录](多宿主机首增量验证_2026-09-20.md)。

## 1. 总结论

**参考实现与 SpiderFly 需求部分对齐，但不能直接作为成品合并。**

可直接参考的是底层可靠性机制：Windows Agent 主动连接、按指定机器分发、单机串行、请求去重、事件序列、断线续传、不确定状态、凭据防落盘、安全下载与不可变发布物。

与 SpiderFly 冲突或缺失的是产品主链路：一次性接入码和待审核、调度/非调度模式、单 `.py` 上传、`v1/v2/v3` 顺序版本、AI 修复候选审批、顶部状态条、输入阻断和 Windows 主控 + SQLite 部署。

因此，kk-rpa 应被定位为**通信协议、Agent journal 和状态机的技术样板**，最终能力仍全部实现在 SpiderFly 内。

## 2. 评估口径

| 标记 | 含义 |

## 6. 可复用与禁止照搬

建议复用：

1. `request_id` 幂等命令和参数冲突检查。
2. Agent 本地 SQLite journal、WAL/FULL 耐久化和单调事件序列。
3. 断线重连、ack/replay 和运行状态对账。
4. uncertain 占位，直到 Agent 确认终态。
5. 单宿主机单活动任务的事务约束。
6. 不可变运行快照和 Task/Run 分离。
7. 凭据集中加密、运行时下发、Agent 日志防落盘。
8. 发布物路径安全、大小限制、hash 校验和原子安装。
9. Windows 交互用户登录自启。
10. 停止/完成/断线竞态测试。

禁止直接照搬：

1. Git monorepo + `app.toml` + `pyproject.toml` + `uv.lock` 发布模式。
2. 上传前强制业务 schema、doctor 和 offline test。
3. 管理员预先创建 Robot 并分发长期 token 的接入方式。
4. AI 直接操作失败浏览器并自动恢复的权限模型。
5. package version + Git commit 代替 SpiderFly `vN` 的版本语义。
6. 把 Linux/Docker/PostgreSQL 作为 SpiderFly v1 前提。

## 7. 最终判定

| 问题 | 答案 |
| --- | --- |
| 参考实现是否已满足 SpiderFly 需求？ | **否** |
| 是否有可复用的技术链路？ | **有，主要是 Agent 通信、journal、调度不变式和安全发布** |
| 是否应直接合并参考仓库？ | **不应该**，产品流程和发布模型冲突较大 |
| SpiderFly 下一步应先做什么？ | **先定稿数据模型、Agent 协议和版本/候选状态机，再做最小端到端闭环** |
