## 1. 我们希望得到的使用方式

开发者把反复出现的操作封装成指令；搭建者在代码或简单步骤列表中组合指令；使用者选择已有任务，填写业务参数并取得结果。独立 Python 是当前实现基础，指令化解决的是复用与维护，不要求先扩展所有语言。

本轮对话认可：借鉴影刀的指令组织方式，但使用独立代码实现与运行；方便人工和 AI 阅读、修改、比较和排查。指令不需要个人签署、个人归名或署名后才能运行。

## 2. 保持简单的组织方式

| 内容 | 负责什么 | 初期怎样放置 |
| --- | --- | --- |
| 指令 | 完成一项能说明输入、输出和成功条件的能力 | Python 函数或小模块，按功能注册 |
| 业务流程 | 决定步骤顺序、数据传递与业务规则 | 可读代码；有界面需要时增加统一的流程配置 |
| 运行上下文 | 提供本次输入、目录、配置引用和资源 | 复用现有执行编号、环境变量和运行资料目录 |
| 发布版本 | 固定本次运行依赖的代码与资料 | 开发完成后生成固定内容的版本包 |
| 现有平台 | 账号、排队、触发、执行记录与结果入口 | 继续沿用 SpiderFly，逐步增加所需功能 |

业务使用者不必看到这些内部层次。任务仍是一份可以直接运行的完整工作，不要求用户先创建“程序”再绑定“任务”。

### 网页定位不是必建的元素平台

网页自动化要知道按钮和输入框在哪里。这些定位信息可以直接写在指令里；同一个定位被多处复用时，再提取为常量或小模块。文件、表格和接口指令不需要网页元素。

下面是伪代码，仅说明职责，不是当前浏览器库 API：

```text
导出库存(网页, 店铺, 日期):
    确认当前账号和店铺
    设置日期并核对筛选结果
    点击文字为“导出库存”的按钮
    等待下载完成
    检查文件与必要字段
    返回结果文件与处理数量
```

按钮属性改变，先修改相应指令中的定位。业务流程改变，再调整指令或流程。定位调试能力可以单独增加，不以建设元素管理系统为前置条件。

## 3. 一条公共指令的最小说明

定义与代码就近保存，一份定义用于参数检查、发现入口和使用示例。普通内部函数不必全部成为公共指令。

| 项目 | 说明 |
| --- | --- |
| 身份 | 稳定功能编号、中文名、用途和版本；不含个人姓名要求 |
| 输入 | 类型、必填、默认值、允许值和示例；文件使用可追踪引用 |
| 输出 | 数据字段和类型；运行文件有明确归属与用途 |
| 前置条件 | 必要的页面、账号、环境或输入状态；文字说明与实际检查区分开 |
| 成功条件 | 可观察的结果检查，例如筛选正确、下载完成、必需列存在 |
| 失败规则 | 错误类别、处理提示、是否可以安全重试 |
| 资源 | 需要的浏览器会话、文件、软件以及释放方式 |
| 使用范围 | 示例、已验证场景、已知限制；可选维护联系方式不影响运行 |

“函数没有抛异常”只是技术结果。业务成功需要各指令和完整任务都能解释自己的检查规则。比如空表在某任务中合理、在另一任务中异常，应由明确业务要求决定，不统一写死“行数必须大于零”。

## 4. 接到当前项目的方式

### 先保留已有能力

- 现有 `.py` 上传和执行路径继续使用，不要求旧脚本一次性改写。
- 延续已有 `result.json` 协议；没有提供结构化结果的旧脚本，仍按现有规则处理并标明结果来源。
- 使用已有的每次运行目录，补齐输入、产物索引和交付入口。
- 继续按任务管理运行环境，不为每条指令创建一套虚拟环境。
- 首轮使用现有单机串行队列，不把多机或并行变成指令复用的前提。

当前指令与示例已经可以构建为本地 wheel；平台任务在依赖中声明精确版本后，环境创建与修复会从固定本地目录安装对应文件。姓名任务使用现有“Excel 模板”上传入口取得输入，保存本次副本后复用包内流程，将结果放入 artifacts 目录，并通过既有 result.json 协议报告结果。上传发生在创建任务时，尚无每次运行重新选择文件或填写业务参数的入口。多文件业务应用上传、网页指令编排和完整任务发布绑定继续作为后续设计。

### 同一套定义服务代码和界面

指令源码保存实现；未来流程配置保存受支持的步骤、参数绑定、条件和循环。界面编辑同一份流程配置，不另存一份独立流程事实。复杂 Python 逻辑作为自定义指令调用，不承诺把任意 Python 完整转换成拖拽图。

修改源码后，界面保存参数不应覆盖源码。AI 后续修改应保留已有人工修复，通过针对性差异更新相关文件。这里是维护设计，不是新增每次编辑都要人工审批的流程。

## 5. 运行时容易忽略的约定

### 明确输入与数据类型

订单号可包含前导零；空值和零值不同；业务日期与实际运行时间不同。任务入队时保存实际输入，后续修改默认配置不改变这一批运行的含义。账号凭据通过受控配置引用，不作为普通业务参数展示或记录。

### 先确认状态，再执行动作

网页指令先检查必要账号、页面和筛选状态。登录过期、错误店铺、加载未完成、匹配多个按钮应分别诊断。定位方式并非所有失败的原因；新的定位匹配后，还要验证动作结果。

### 区分重报结果与重做业务

“提交成功但响应丢失”属于结果未知，应先按业务标识查证。临时读取失败可有限重试；输入错误需修正输入；停止任务只阻止后续操作，不承诺撤销已有提交。批处理需要逐项记录已完成、失败、未处理与待确认的项目。

### 恢复需要版本和状态

恢复默认使用原发布版本、原输入和校验过的业务进度。浏览器对象和 Excel 实例只在当前运行中有效，不能当成可跨机器、跨重启持久化的数据；需要重新准备页面或连接。更新过的流程能否读取旧进度，要有明确兼容判断。

### 目录、资源与清理

任务的临时文件和长期结果应分开。当前公共工作目录会清理，交付文件放入受管理的运行产物区。浏览器、文件和桌面会话明确归属，正常完成、异常、超时与取消都考虑资源释放。并行能力在实际隔离验证后再增加。

## 6. 方便修改与稳定运行如何同时实现

开发状态允许直接修改源文件。发布状态固定流程、指令、公共核心、依赖与模板，每次运行绑定具体发布版本。

公共指令或定位修复后，查看使用它的任务，验证相关流程，再选择升级。没有单独抽出的定位，直接跟随所在指令发布；有共享定位时，把共享定义及依赖关系一起纳入版本。保留旧版本供回退及原运行恢复，运行到一半不切换实现。

参考项目的应用快照机制值得借鉴，但实际应用仍通过 editable 相对路径引用公共核心。仅固定元素和指令副本，并不能固定这份核心源码。我们的发布方案应固定完整依赖内容，或固定完整仓库版本与所需路径，而不把可变开发目录当作完整发布包。

参考依据：[应用依赖配置](https://github.com/wjiajian/kk-rpa-monorepo/blob/d941a9d4265d5db2defb4df9707148ef57dd5ad7/apps/inventory_jushuitan_export_stock/pyproject.toml)、[快照实现](https://github.com/wjiajian/kk-rpa-monorepo/blob/d941a9d4265d5db2defb4df9707148ef57dd5ad7/packages/rpa-core/src/rpa_core/catalog.py)。

## 7. 第一次验证的范围

建议选两个不同任务，复用三到五个实际重复动作。候选场景可以是库存日报和订单差异检查；它们目前只是举例，尚未选定真实业务。

验证至少回答：

1. 两个任务是否调用同一份指令实现，而非复制两份代码？
2. 更换日期、文件等输入，是否无需修改源码？
3. 输入缺列、错误页面或定位失效时，是否能准确解释原因？
4. 使用者能否取得结果文件并理解部分失败？
5. 修复指令后，能否只升级选定任务并保留历史？
6. 旧脚本是否仍可运行，未参与开发的人是否能独立完成一次操作？

涉及外部提交时，另验证响应丢失与重复处理；没有这类动作的首轮示范，不声称已验证写入恢复。

## 10. 第二轮补充：从“能运行”继续检查“能维护、结果可信”

以下均为补充设计，当前状态仍见台账。只在真实示范需要时实现对应部分，不扩大成完整工作流或数据平台。

### 业务完成、结果交付和清理分别记录

当前通知状态已有单独记录，可沿用这个思路区分业务、交付与运行收尾。例：订单已确认提交，但清理临时文件失败，应补清理；文件已生成并检查通过，但上传失败，应补交付。对无法确认的外部动作保留“结果待核实”，不能因本地结果损坏就认定对方没有执行。

文件交付可以先生成临时文件、检查内容，再发布为正式产物。这里借鉴暂存与提交的分离，不宣称本地文件处理能回滚所有外部动作。参考：[Prefect 事务说明](https://docs.prefect.io/v3/advanced/transactions)。对应 OPT-013。

### 保存失败样本，用同一输入比较新旧实现

将已经读取的必要数据保存成受控调试样本，记录来源、时间、范围、内容摘要和版本。修改清洗、解析或报表逻辑时，可以离线使用样本，并对比新旧结果的业务差异，减少重新登录和下载。

样本运行与真实运行明确区分；样本调试路径不调用真实写入，外部动作由测试替身处理。离线通过仅说明该样本对应的数据处理行为，不证明当前网页定位和登录仍有效。类似机制可参考 [n8n 固定与模拟数据文档](https://github.com/n8n-io/n8n-docs/blob/main/docs/build/work-with-data/pin-and-mock-data.md)，本项目无需因此引入 n8n。对应 OPT-014。

### 检查字段的业务含义，并独立核对完整结果

数字类型不能表达金额是元还是分，行数也不能说明一行是一张订单还是一条明细。先在具体场景约定必要语义，再决定是否抽成公共字段规范。

除了指令自己的结果检查，完整任务还需要少量独立业务依据。分页漏一页、拿到旧文件或选错店铺，应通过来源与筛选信息、主键或汇总核对发现。检查输出期望值、实际值与差异，并区分提醒与停止；不要把任何空表都当作失败。可借鉴 [Dagster 数据检查](https://docs.dagster.io/guides/test/asset-checks)的独立检查思路。对应 OPT-015。

### 修复必须保持业务规则，减少“改到不报错就结束”

给指令留少量有意义的反例：两个候选按钮不能任取其一，缺少必需业务标识不能悄悄跳过。修复后的代码需要通过这些反例；真的改变业务规则时，记录新的规则与验收依据。保留源码不被覆盖与保持业务含义都需要考虑。对应 OPT-016。

### 让人找得到能力，并判断是否值得复用

代码旁的说明同时提供常见业务叫法、适用与不适用场景、示例和替代入口。让未参与开发的人尝试查找并调用，观察是否仍要复制修改大段代码，以及一次故障修复花多久。先用这些具体记录验证收益，不增加指令商城或运营看板。补充 OPT-001、OPT-011。

开发者可以在现有编辑器或 Codex 中直接维护源码。提供轻量本地调试入口，运行同一条指令时不必先启动整套网页服务；平台执行与本地调试共享实现，只注入不同运行上下文。无需为了代码优先再制作一套网页代码编辑器。补充 OPT-004。

### 共享使用时明确执行边界

独立 Python 环境管理依赖版本，不能限制代码对宿主账号可访问文件和网络的使用。当前可信管理员上传代码的边界已写在 README 中；将来如果允许更多人上传代码，应单独考虑运行身份和权限隔离。普通同事运行已发布任务与开发者修改源码可以采用不同权限，不以简单的权限声明冒充实际隔离。补充 OPT-008。
